Rules, method and the decision workflow

Rules applied to every row

  1. R1 — Single-entry / freezeout test. A row is labeled 'single entry per official structure sheet' only when all three hold: (1) the schedule row is a one-day or single-start event, (2) that event's structure sheet was read in full in this session, and (3) the sheet prints no re-entry, re-buy or add-on provision. Silence is weaker than an explicit statement, so the label always names its own basis. Rows whose sheet prints a fee discount, a 'subsequent buy in' clause, or a multi-flight structure are NOT labeled single entry.
  2. R2 — Ranking and the guarantee ratio. Ranking is allowed only for rows where BOTH the total entry fee and the guarantee are confirmed from the official sheet. The ratio shown is guarantee ÷ entry fee, which counts how many entries are needed to reach the guarantee. It is a descriptive ratio of published numbers, not a forecast of overlays, and it is not a per-entry expected value. Bounty events carry a guarantee that the sheet says includes bounties, so their ratio is not comparable with a pure cash-pool ratio; those rows are labelled Bounty / PKO. Multi-flight rows are labelled Flight.
  3. R3 — One event per day, overlap check. Each day gets one primary event (earliest confirmed start that day) and, where one exists, one conditional fallback: a later event on the same date whose start is after the primary's official late-registration close and at least 4 hours after the primary's start. 4 hours is a documented planning assumption - no official source publishes event durations. Any other same-day row is marked 'cannot be added to the primary' because its registration window is still open while the primary is running.
  4. R4 — Walking limit. A hotel qualifies only if the walk from its lobby to the poker room is 30 minutes or less. Official pages publish addresses, not walking minutes, so a pair with no measured time is shown blank and flagged. Third-party minute ranges are never promoted to verified; they appear only with a Google and Apple Maps link for the reader to time.
  5. R5 — True hotel cost, like-for-like. True nightly cost = room rate + mandatory resort fee + room tax. It is only computed when all three are known for the same dates, the same occupancy and the same room type; otherwise the row stays blank. Quotes are kept as a dated log (rate timestamp, checkout total, nightly average, resort fee, tax, parking, cancellation deadline), never as one flat number.
  6. R6 — Verification, last-checked and source-change monitoring. Every row carries its official source link, the date the source was read, and its verification label. Values that cannot be confirmed are blank and appear on the Flagged for Review page. A scheduled GitHub Actions job re-fetches every official URL each morning, compares the stored snapshot with the live page, marks rows whose source changed, and appends to a dated change log; the site is then rebuilt.

How to use this site, in order

  1. Fix the trip dates and a nightly budget/quality floor (Q1, Q2).
  2. For the candidate events, open each structure sheet link in the table and read the printed maximum-entry / no-rebuy / no-add-on wording; drop anything that does not meet the single-entry policy (the advantage page is what gets dropped and why).
  3. Compare only the surviving events on guarantee, buy-in, starting stack and blind duration, payout percentage and whether the schedule fits the day.
  4. Get an itemised hotel total for the same stay and time the walk (≤30 min) with the map links on the routes page.
  5. Build one event per day first; add an evening event only where the primary event's field is closed and the gap is real (rule R3).
  6. Re-confirm schedules, rates and cancellation policies on the official pages before any non-refundable payment — the monitoring page records when each source was last fetched and flags changes.

Field-size note

The DSE "Results" column is empty on the official page for every row read today, so entries-per-event and therefore the actual overlay situation are unknown. The "entries to reach GTD" column is the guarantee divided by the amount each entry adds to the pool (the buy-in minus the withheld house fee), which is the arithmetic the room itself would run; the buy-in-based figure is in each cell's tooltip. It is a description of the printed numbers, not a forecast of field size, and no overlay or shortfall is implied.
