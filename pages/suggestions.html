Suggestions: choose a path before anything changes

19 improvements, each with the options and what each one costs you. Pick one option per suggestion and the list at the bottom becomes your change request. Nothing on this site is altered until you ask for it.

S01. Put a one-line entry rule on every table row

Problem: A reader cannot tell at a glance whether an event is a freezeout, a re-entry or simply unknown.

Effect: The second option costs one more column and removes most misreads. It does not change any data.

S02. Ask the poker rooms for a written single-entry statement

Problem: Silence on a structure sheet is not a one-entry promise, so nothing can be confirmed as a freezeout.

Effect: Only the first two can move an event from unverified to confirmed. Until then a freezeout plan is an assumption.

S03. Capture dated hotel quotes instead of a single number

Problem: Room rates move daily; a single figure goes stale and the true nightly cost with it.

Effect: The log is the only option that keeps a like-for-like history. Screenshots make disputes resolvable.

S04. Time the walks yourself and record them

Problem: No official source publishes hotel-to-poker-room walking times, so the 30-minute filter is nearly empty.

Effect: The first option makes the filter useful and stays honest. The third fills the table but is not an official value.

S05. Run the official-source check every morning, not once a day at random

Problem: Schedules, structures and fees change without notice.

Effect: A morning run matches the brief's 'pull the schedule each morning'. Twice daily catches intraday changes at double the Actions minutes.

S06. Publish one site instead of thirteen session dashboards

Problem: Earlier sessions each left a dashboard in its own folder; the same question has several different answers.

Effect: The first option gives one answer per question and keeps earlier work reachable. Deleting loses source history.

S07. Price a plan that assumes one entry, and one that assumes re-entry

Problem: A multi-entry event can cost two, three or more buy-ins; a plan that assumes one entry understates the cost badly.

Effect: Side-by-side totals make the downside visible before you commit money.

S08. Reconfirm everything before any non-refundable payment

Problem: Every value here is a snapshot from an official page on 2026-11-17.

Effect: Refundable rates are the cheapest insurance; Caesars and Horseshoe advertise free 48-hour cancellation and Resorts World requires 48 hours' notice for a deposit refund.

S09. Capture dated stay quotes automatically in the morning job

Problem: The dated rate log currently holds hand-captured booking-engine snapshots; the trip planner stays Incomplete without a quote for the chosen dates and occupancy.

Effect: A fresh dated quote per hotel per morning would make true nightly cost comparable like-for-like and let the planner complete honestly.

S10. Adopt a like-for-like comparison policy before any hotel ranking

Problem: Existing captures differ in stay window and occupancy (2 adults Dec 2-9 vs 1 adult Dec 13-20), so 'cheapest hotel' cannot be derived from them.

Effect: Prevents a false ranking; the flagged page already refuses to name a cheapest hotel.

S11. Decide how walking minutes get verified

Problem: No official source publishes walking times between properties; the brief wants a 30-minute walking filter.

Effect: The 30-minute filter can only be honest about measured or officially stated minutes.

S12. Decide the fate of the 13 archived session dashboards

Problem: Earlier session folders are published alongside the root site and disagree with it on some numbers.

Effect: Reduces reader confusion when an archived page shows an older verdict count.

S13. Publish one root-site generator (done here) and retire the second one

Problem: Two scheduled jobs each rebuilt the root site from different data with different verdict standards, so the published headline changed every night depending on which job committed last.

Effect: The site is reproducible: `python3 scripts/integrate_b3be876c.py && python3 scripts/build_ea99006a.py` regenerates every published page, and quality.yml proves the committed output matches.

S14. Keep value-level monitoring, drop hash-level alarmism

Problem: Hashing a whole casino page produces a 'change' on every request (tokens, timestamps), which buries real edits in noise; 48 of 96 ledger entries were 'changed' on the first run.

Effect: A row is marked 'source changed' only when the sentence behind its value changes.

S15. Filter the tables by whether an event is actually open to you

Problem: Single-entry rows can still be closed fields: the 2 and 8 December Seniors events pass S1 but are 50+, two LIPS satellites are female-only, and one event is a two-player tag team. Before this session they were ranked as ordinary picks and could become a day's primary event.

Effect: The label is implemented and the ranking plus the day schedule already exclude restricted rows. A reader-side toggle is the natural next step but needs a decision on what 'eligible' means (age and gender are the reader's own facts, not the site's to assume), so it is left as an option.

S16. Have the monitor record its first-read baseline explicitly

Problem: The whole-page ledger has no successful first read recorded, so its 'changed' marks are unproven and 94 schedule rows carry a page-level note that has nothing to do with their values (flag F57).

Effect: Option 2 costs one scheduled run of extra latency and removes the misleading first-run badges; it does not change any published value.

S17. Nightly calendar capture for the hotels whose booking engines render server-side

Problem: The Horseshoe and Resorts World calendars returned full December price maps in one read (2026-11-19), while the Venetian and Caesars Palace engines returned nothing. One nightly scheduled capture of the two working engines would turn the rate log into a real price history.

Effect: Price history and change badges for hotel rates, like the ones event rows already have. In review - not implemented.

S18. Show both directions of every walk and let the filter use the direction that matters

Problem: Walking routes are asymmetric (Wynn to Venetian 14 min vs Venetian to Wynn 26 min; flag F72). The table shows one direction per row; a reader deciding on the walk home after midnight sees the reverse row only if they look for it.

Effect: Safer late-night planning. In review - not implemented.

S19. Store the GTD to entry-fee ratio as a data field

Problem: The ratio is computed at render time (schedule tables, planner) but is not a stored field, so it cannot be sorted or exported from the data files alone.

Effect: Makes the ranking reproducible outside the site build. In review - not implemented.
